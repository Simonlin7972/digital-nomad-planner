## 背景

*從 repo 文件整理的現況：*

- **產品現況：** 網頁版（Vite + React）可以排 2025–2028 的行程，資料存在瀏覽器 localStorage。手機版面（720px 以下）**只能看不能改**，內容有「現在／下一站」卡片、行程卡片、摘要、地圖（MVP.md「手機」一節）
- **既有的跨裝置搬移：** JSON 匯出／匯入，以及「傳到其他裝置」連結 `/app/#plan=<代碼>`（deflate-raw 壓縮後 base64url，不經伺服器）
- **已經在模擬原生體驗的部分：** 可加入主畫面、手寫 service worker 支援離線、機票「加入行事曆」下載 `.ics`、系統分享選單
- **明確不做（MVP.md）：** 登入、雲端同步、手機上編輯。「選用的雲端同步」列在之後的方向第 8 點
- **路線圖：** iOS App 目前不在 MVP.md 的「之後的方向」裡，這份 PRD 是第一次提出
- **競品：** [PLACEHOLDER：repo 沒有競品資料。待補：Nomad List、TripIt、Wanderlog、Polarsteps 在「整年行程」與「小工具」上的做法]

## 問題

數位遊牧者在**電腦上**排好一整年的行程，但真正需要查的時候人在**路上**：機場報到、入境填表、跟房東約入住、算申根還剩幾天。現在的手機網頁版有這些問題：

1. **要主動打開才看得到。** 沒有桌面小工具、沒有通知，「下一站幾天後出發」得自己想到才會去查
2. **資料留在瀏覽器裡，容易不見。** iOS Safari 對很久沒開的網站會清除 localStorage（ITP 7 天規則對加入主畫面的網頁 App 較寬鬆，但規則不透明），行程有可能默默消失
3. **加入主畫面的門檻高。** 很多人不知道 Safari 可以這樣做，跟 App Store 下載比起來不容易被發現
4. **不夠原生。** 行事曆要下載 `.ics` 再打開、分享繞了一層，手感跟原生 App 有差

## 解法

### 運作方式

**SwiftUI 原生 App，定位是網頁版的隨身版。** 電腦上用網頁版規劃，手機上用 App 查行程、收提醒、看小工具。

**資料流：**

```
網頁版（電腦）──「傳到其他裝置」連結／QR code ──▶ iOS App
網頁版（電腦）── JSON 檔（AirDrop、檔案 App）──▶ iOS App
iOS App ── 匯出 JSON／產生傳送連結 ──▶ 網頁版
（第二階段）iOS App ◀── iCloud（CloudKit）──▶ 其他 Apple 裝置
```

**範圍分級：**

| 優先級 | 功能 | 說明 |
|---|---|---|
| **P0** | 行程瀏覽 | 對齊手機網頁版：現在／下一站、行程卡片、空檔、已結束收合、年份切換、摘要（申根 90/180、台灣 183 天）、地圖（MapKit） |
| **P0** | 匯入 | Universal Link 打開 `#plan=` 連結直接匯入；從檔案 App、AirDrop 開 `.json`；規則照 MVP.md（會取代有行程的年份時先問；格式錯誤或重疊的項目略過） |
| **P0** | 匯出 | JSON 透過系統分享選單匯出，也能產生傳送連結，讓資料可以回到網頁版 |
| **P0** | 桌面與鎖定畫面小工具 | 小、中尺寸與鎖定畫面：現在在哪、第幾天／共幾天、下一站與倒數。午夜自動更新（timeline 排程，不需要網路） |
| **P0** | 本地通知 | 出發前一天提醒（有機票就附航班）、申根天數快到上限時提醒；全部用本地通知，不需要伺服器 |
| **P0** | 加入行事曆 | 用 EventKit 直接寫入，取代下載 `.ics`；只在使用者按下時要權限 |
| **P0** | 三種語言 | 繁中、英文、日文，跟網頁版一致；國名改用 `Locale.localizedString(forRegionCode:)` |
| **P1** | 簡易編輯 | 用表單新增／修改／刪除一段行程（國家、城市、起訖日、顏色、機票、備註），**不做時間軸拖曳**。守住不重疊規則 |
| **P1** | 分享圖 | 直式 9:16 PNG（對齊網頁版 `renderPortraitPng`），用 SwiftUI `ImageRenderer` 畫 |
| **P2** | iCloud 同步 | CloudKit 私有資料庫，同一個 Apple ID 的 iPhone／iPad 同步；跟網頁版之間仍用連結與檔案 |
| **P2** | 移動日 Live Activity | 出發當天在鎖定畫面與動態島顯示航班與起飛時間 |

**共用資料，避免兩邊不一致：** 季節（`seasons.ts`）、國定假日（`holidays.ts`）、城市清單（`cities.ts`）由網頁版 repo 在 build 時輸出成 JSON，App 直接帶這份 JSON，不在 Swift 手抄一份。日期、規則這類邏輯（`weeks.ts`、`stayRules.ts`、`sanitize`）改寫成 Swift，並用同一組測試資料比對兩邊的輸出。

**資料格式：** App 讀寫的格式跟網頁版的 `version: 2` 匯出檔完全一樣。App 內部用 SwiftData 或單一 JSON 檔存，放在 App Group，讓小工具也讀得到。

### 使用者故事

**故事 1：從電腦搬到手機**
- **身為** 在電腦上排好 2027 行程的遊牧者
- **我想要** 用 iPhone 相機掃網頁版的 QR code，直接在 App 裡看到行程
- **這樣** 不用處理檔案，也不怕 Safari 清掉資料
- *邊界情況：* App 已經有 2027 行程時，先列出會被取代的年份請我確認；連結被截斷時顯示「這個連結讀不出行程」

**故事 2：不打開 App 也知道下一站**
- **身為** 正在清邁住第 23 天的遊牧者
- **我想要** 在桌面小工具上看到「清邁 第 23／30 天，7 天後飛峴港」
- **這樣** 跟房東續約或訂接送時不用翻資料
- *邊界情況：* 兩段行程之間有空檔時，顯示「空檔中，N 天後到 X」；今天以後都沒有行程時，顯示「還沒有下一站」並引導回網頁版規劃

**故事 3：出發前被提醒**
- **身為** 明天要飛的遊牧者
- **我想要** 前一天晚上收到通知，內容有航班號和起飛時間，點一下就能複製訂位代號
- **這樣** 不會臨時才找行程細節
- *邊界情況：* 時間照使用者填的顯示，不換算時區（跟網頁版一致）；之後匯入的資料改了日期時，舊的通知要取消重排

## 不做的

- **時間軸拖曳編輯、月曆檢視：** 規劃還是在電腦上做，App 不重做網頁版的年檢視
- **帳號登入、自己架的後端：** 維持「免登入、免後端」。iCloud 是 Apple 的服務，不算自架
- **網頁版與 App 自動同步：** 兩邊之間只靠連結和檔案；要做自動同步就得有後端，跟上一條衝突
- **Android 版**
- **iPad 專用版面：** iPad 照 iPhone 版面放大，第一版不另外設計
- **App 內購買、廣告**
- **用 WebView 包網頁版：** 避開 4.2 條款，也做不到原生手感

## 依賴項目

### 功能依賴

- **網頁版輸出共用資料 JSON：** 季節、假日、城市清單要能被 App 使用，需要在網頁 repo 加一個 build 步驟。狀態：未開始
- **網頁版的「傳到其他裝置」連結改成 Universal Link 可以接手的網址：** 狀態：連結已存在，網址要配合下一條調整
- **資料格式 `version: 2` 凍結：** App 上架後，網頁版改格式必須保持向下相容。狀態：要寫進 CLAUDE.md 當成規則

### 人力依賴

- **設計：** App 圖示（以像素吉祥物為基礎）、小工具版面、App Store 截圖。時程：開發第 1–2 週
- **開發：** 一人（Simon + Claude Code）。SwiftUI、WidgetKit 經驗 [PLACEHOLDER：自評]

### 外部依賴

- **Apple Developer Program：** US$99／年。開始 TestFlight 之前就要有
- **Universal Link 的網域：** `apple-app-site-association` 必須放在網域根目錄的 `/.well-known/` 底下。現在網站是 GitHub Pages 的**專案頁**（`simonlin7972.github.io/digital-nomad-planner/`），專案 repo 沒辦法放檔案到網域根目錄。兩種做法：(a) 在 `simonlin7972.github.io` 這個使用者頁 repo 放這個檔案；(b) 換成自訂網域。**沒解決的話，掃 QR code 會打開 Safari 而不是 App**
- **App Store 審核：** 4.2「最低功能要求」、隱私標籤、匯出加密聲明（只用 HTTPS，屬於豁免）
- **字型授權：** 975 朦朧黑體、Pixelify Sans 要確認允許嵌入 App（OFL 通常可以，要看實際授權文字）
- **地圖：** 改用 MapKit（免費、不需要金鑰），不用 MapLibre 和 OpenFreeMap
- **地點座標：** Nominatim 的使用政策要求帶可識別的 User-Agent、每秒最多一次請求。App 可以考慮改用 `CLGeocoder`（Apple 內建），就不用遵守第三方政策

**關鍵路徑：** **Universal Link 網域。** 它決定「從網頁搬到 App」這個核心流程能不能一步完成；如果決定換自訂網域，還會牽動網頁版的 `og:url`、GA 設定和既有連結。要第一個處理。

## 風險

*類型：V=價值、U=易用性、F=可行性、B=商業可行性。影響：H=高、M=中、L=低*

| 風險 | 類型 | 影響 | 對策 |
|---|---|---|---|
| 審核以 4.2「只是網站的重新包裝」或「功能太少」退件 | B | H | 原生 SwiftUI，不用 WebView；第一版就帶小工具、通知、EventKit；送審說明強調這些功能。真的被退，就把 P1 簡易編輯提前 |
| App 不能編輯，使用者覺得功能不完整，給低分 | V | H | 首次打開時說清楚「電腦規劃、手機隨身」；P1 簡易編輯排在 1.1 版，視 TestFlight 回饋決定要不要提前 |
| 網頁版和 App 的規則算法不一致（例如申根天數不同） | F | M | 共用資料改成 build 時輸出；規則邏輯用同一組測試資料比對兩邊輸出 |
| 搬資料的流程卡住（網域問題、連結太長） | U | H | 先處理 Universal Link；同時支援 JSON 檔；連結失敗時提示改用檔案 |
| 兩邊各自改了行程，使用者搞不清楚哪一份是新的 | U | M | 匯入前顯示兩份的最後修改日期；「不做的」寫清楚兩邊不會自動同步；P2 iCloud 只處理 Apple 裝置之間 |
| 一個人要同時維護網頁版和 App，負擔太重 | B | M | App 範圍刻意縮小（不做時間軸）；共用資料來源只有一份 |
| 上架後沒有數據可以判斷成效（沒放 GA） | B | L | 先看 App Store Connect；需要時再評估隱私友善的統計，並更新隱私標籤 |

### V/U/F/B 檢查

| 風險類型 | 問題 | 狀態 |
|---|---|---|
| **價值** | 使用者會想要手機上的隨身版嗎？ | ⬜ 要先看 GA 手機回訪資料，再做訪談 |
| **易用性** | 從網頁搬到 App 能不能一步完成？ | ⬜ 卡在 Universal Link 網域 |
| **可行性** | 一個人做得出 SwiftUI App 加小工具嗎？ | ✅ 邏輯簡單，又是不碰 UI 的純函式，範圍可控 |
| **商業可行性** | 審核過得了？免費、沒有收入，值得花時間維護嗎？ | ⬜ 審核風險中等；維護成本要訂停損點 |
