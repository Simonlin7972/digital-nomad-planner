# CLAUDE.md

Guidance for Claude Code working in this repository.

## What this is

A single-page planner for a year of digital nomading (2025 to 2028; 2027 by default). Vite + React 19 + TypeScript, no backend; all data lives in the browser's `localStorage`. The UI is in Traditional Chinese, English and Japanese.

- Product behaviour and decisions: [MVP.md](MVP.md)
- Setup, data format, structure, design notes: [README.md](README.md)

## Commands

```bash
npm run dev      # dev server: landing page on http://localhost:5173/, the app on /app/, the design system on /design/, the pixel guide on /pixel/, the demo canvases on /demo/ (strict port)
npm run build    # tsc --noEmit, then vite build
npx tsc --noEmit # type-check only
npm run record:picker  # re-record docs/picker-demo-4x5.mp4, the country / city picker video (needs Chrome and ffmpeg, ~5 min)
```

There are no tests and no linter. `tsc --noEmit` is the only automated check, so run it after every change.

## Keep the docs in sync

Whenever a change adds, removes or alters behaviour, update in the same piece of work:

- **README.md** — features, controls, data format, project structure, known limits, third-party resources
- **README.en.md** — the English translation of README.md; mirror every README.md change there, section for section
- **MVP.md** — the spec for the affected area, the decision table if a decision changed, and one line in the changelog
- **CLAUDE.md** — only when a convention, invariant or workflow described here changes
- **CHANGELOG.md** — one user-facing line for what changed, in Traditional Chinese with an indented `EN:` line below it, under today's `## YYYY-MM-DD` heading (add the heading if it isn't there; newest day first). It is the source of the public /changelog/ page and is published with every push, so write for people using the planner, not about code. Skip it only for changes nobody using the site would notice, and say so

A Stop hook (`.claude/hooks/docs-check.sh`) blocks once when code under `src/` or a page entry (`index.html`, `app/index.html`, `changelog/index.html`, `profile/index.html`, `cities/index.html`) has changed without all four files being touched. If a file genuinely needs no change, say so explicitly rather than editing it for the sake of it.

## Architecture you need to know

- **Layout.** `src/App.tsx` owns the plan and page-level state and wires things together. `src/components/` holds the UI (each with its `.css` beside it), `src/hooks/` the stateful helpers, `src/lib/` everything that isn't UI. Views own their own drag state and report results through callbacks; they never hold the plan.
- **Dates are day indexes.** Day 0 is the Monday of the week containing 1 Jan of `YEAR` (2026-12-28 for 2027), so `day % 7` is the weekday. `YEAR` and the date model built from it (`WEEKS`, `DAY0`, `TOTAL_DAYS`, `SLOTS`, `MONTHS`) are live `let` exports of `lib/weeks.ts`; `setYear` rebuilds them, saves `dnp-year` and notifies, and `App` remounts the page keyed by year. So never copy them into module-level constants (compute per call, as `storage.ts` does with `planKey()`), and never reload the page to change year. Never hard-code a year: use `YEAR`, `DAY0`, `monthRange`. Each year has its own plan (`dnp-plan-<year>`). Holiday data exists for 2026 and 2027; `holidaySets` returns none for other years, and clips holidays to the timeline so the borrowed days at either end show their neighbours' holidays. A stay is `{ startDay, endDay }` inclusive in memory and ISO strings on disk. Helpers are in `src/lib/weeks.ts`.
- **The year view is approximate, the data is exact.** The timeline has two half-week slots per week; each end of a stay snaps to the nearest slot boundary for drawing only (`slotsOf`). At 300% zoom and above `YearView` switches its grid to one column per day (see `gridOf`): everything positional there goes through the current `Grid` (`cols`, `boundary`, `n`, `perWeek`), never `SLOTS` or `slotsOf` directly, and a drag keeps the unit it started with. Never round the stored dates to fit the display.
- **Stays share at most one travel day, and never across years.** A stay's last day may be the next one's first (`sharesDay`), provided both are longer than that day, so no day belongs to more than two stays; any other overlap is a clash (`clashes`, `fits` in `lib/storage.ts`). Every path that changes stays must keep this true. Edge drags may create a travel day (`pushStays` lets the dragged edge land on the neighbour's first or last day before pushing it); moving a whole stay, alt-copies and splits never do, and pushed stays keep the link they had to the next one. Views draw a travel day split between the two stays (`travelDays`, `travelSlotsOf`). Any total of days must count each day once: use `daysCovered` from `lib/weeks.ts`, never a sum of `daysOf`.
- **A stay with a ticket is locked** (`isLocked` in `lib/storage.ts`): `pushStays`, `reorderStays`, `splitStay` and `insertStay` refuse to move, cut or pass it, and the views give it no handles. Only the editor changes its dates. Any new position logic must treat locked stays as walls.
- **A stay may cross into the next year.** It is kept in the plan of the year it starts in: `startDay` is on the timeline, `endDay` may run past `TOTAL_DAYS` up to `spillLimit()`. Anything that draws or totals by the timeline clips (`slotsOf` does, `daysOnTimeline` for counts); `dayOfIso` only accepts timeline days, `dayOfIsoAny` any. What the neighbouring years' plans take up is `Edges` in `lib/storage.ts`: App works it out with `computeEdges()` whenever the stays change and stores it with `setEdges`; `pushStays`, `reorderStays`, `insertStay`, the views' selection and the editor's date limits read `getEdges()` (`lo`, `lastStart`, `hi`), and the neighbours' stays that reach onto this timeline are `ghosts`, drawn faded in both views and never edited here (a click switches year). `gapsOf` and `checkSchengen` read it too, the Schengen window looking back through last year's plan.
- **All plan changes go through `setStays` in `App.tsx`** (from `useHistory`). It pushes onto the undo stack. Do not write to `localStorage` or mutate stays any other way. The one exception is import, which writes the years not on screen with `saveYearPlan`.
- **Export and import cover every year.** The file is `{ version: 2, years: { <year>: <single-year plan> } }` (`serializeAll` / `sanitizeAll` in `lib/storage.ts`); a single-year file still imports, into the year it names. Other years are read and checked with `inYear(year, fn)` from `lib/weeks.ts`, which runs `fn` with that year's date model and puts the current one back.
- **Position logic is pure and lives in `src/lib/storage.ts`.** `reorderStays` (dragging a whole stay: list-style reorder), `pushStays` (stretching an edge: shove neighbours), `insertStay` (alt-drag: insert a copy, never moving anything before it, shifting what follows later) and `splitStay` (hold B and click: cut one stay in two; the second part gets a new id and no ticket). During a drag they are recomputed from the original stays on every pointer move, so no drag state accumulates.
- **Every import goes through `applyImport` in `App.tsx`**: the JSON file (menu or dropped on the page) and the "send to another device" link (`lib/transfer.ts`, the plan compressed after `#plan=`). `takeTransferHash()` runs in `main.tsx` before `initAnalytics()` so the plan never reaches the page address GA records; keep it first, with `takeAuthCode()` (the Google sign-in code in `?code=`) right after it and before analytics in both `main.tsx` and `profile/main.tsx`. A link import is not a backup (no `markBackedUp`).
- **Cloud sync is a second copy, never the working copy.** Signed in with Google (`lib/cloud.ts`, Supabase project shared with Wordrobe, schema `nomad`: `plans` one row per user and year holding the `serialize()` object, `settings` one row holding the `Profile`; the SQL is `docs/nomad-schema.sql`, the migration itself lives in the wordrobe repo, and Exposed schemas / redirect URLs are dashboard settings), `hooks/useCloudSync.ts` pushes a changed year 1.5 s after it changed and reads the cloud on sign-in, focus, reconnect and Realtime events. What comes down is applied through `onPull` in `App.tsx` the way an import is (this year via `setStays`, other years via `saveYearPlan`); nothing else writes `localStorage`. The decisions are pure in `lib/sync.ts`, keyed by the `dnp-sync` record (per-year fingerprint + cloud `updated_at`): a side that moved on is copied over the other, both moved means the later one wins, and only a first sign-in with two different plans asks; the sync never deletes a row (an emptied year is an empty row, so emptying propagates), and a row that is gone is re-uploaded rather than clearing a device (`SyncConflictDialog`; "later" pauses everything until `SyncPaused`'s button). Phones pull only, except on their first sign-in. Cloud rows are cleaned with the same `sanitize` / `sanitizeProfile` as a file, so the cloud format is the export format and needs no versioning of its own. supabase-js is never imported statically: `cloud.ts` imports only its types and loads the library through `client()` (a dynamic `import()`) when something could be a session (`mightBeSignedIn`: the `sb-<ref>-auth-token` key in `localStorage`, or a sign-in code `takeAuthCode` just took from the address) or when `signIn` is pressed; `onSession` answers null at once otherwise. Keep `takeAuthCode` synchronous and free of the library, and add no static import of `@supabase/supabase-js` anywhere, or every visitor downloads the 220 kB chunk again (check the `modulepreload` links in `dist/app/index.html` after a build). The settings page has its own `hooks/useSettingsSync.ts` that touches only the settings part of `dnp-sync`. Deleting cloud data also signs out every device (`scope: 'global'`; any device left signed in would push its plan straight back up), while an ordinary sign-out is this device only. The anon key in `cloud.ts` is public by design; RLS is the boundary.
- **Offline is a hand-written service worker** (`public/sw.js`, registered by `lib/offline.ts` in production only). It keeps same-origin files and the two font hosts, nothing else. Bump `CACHE` in it if its caching rules change. Testing it needs `npm run build` and the `preview` launch config; a production build loads GA, so open it with `?internal=1`.
- **Imports are sanitised.** `sanitize` drops malformed or overlapping entries and accepts two legacy formats. New fields on `Stay` need handling in `serialize`, `sanitize`, the editor, and the README data-format section.
- **The PNG export is drawn separately** in `src/lib/exportPng.ts` on a canvas, in two layouts (`renderPng` landscape, `renderPortraitPng` 9:16). New visual elements do not appear there unless added. It is opened from the Share dialog (`components/ShareDialog.tsx`), which previews the image before download. Flags are drawn from the URLs the flag-icons stylesheet resolved; keep flight details and booking references out of the image.
- **Phones are read-only.** Below 720px, or on a touch screen under 500px tall (a phone on its side), `App.tsx` swaps the timeline, calendar and list for `components/MobileItinerary.tsx` and never opens the editor. Anything new that edits the plan belongs in the desktop branch only. The query is `NARROW_QUERY` in `hooks/useNarrow.ts`; phone CSS uses the same media query, not a bare `max-width: 720px`. `MobileItinerary`'s now / next card reads every year's plan; the phone's switch to the current year happens in `App.tsx` before the first render, never from an effect, since switching while a plan is mounted would save it under the new year.
- **Places are stored language-neutrally.** A stay's `country` is an ISO code or region id and its `city` the listed city's English name; unlisted values are kept as typed. Show them with `countryOf` / `cityOf` / `placeName` / `placeFull` from `lib/storage.ts`, never the raw field. `normalizeCountry` / `normalizeCity` convert typed or legacy names on save and on load.
- **Country names come from the browser.** `src/lib/flags.ts` builds the list from `Intl.DisplayNames` plus a few regions and aliases. The pickers (`src/components/Combobox.tsx`) still accept free text, so never assume a stay's country or city is on a list.
- **The city list is a typing aid.** `src/lib/cities.ts` holds a hand-written `[Chinese, English]` list per ISO code. It is deliberately incomplete and carries no coordinates; unlisted cities are normal and get no warning. `POPULAR` there is a hand-ordered list of `code/English name` keys that leads the city list when no country is chosen; a key must match a listed city or it is skipped. `src/lib/airlines.ts` is the same kind of list for the ticket's airline (IATA code, Chinese, English, home country); a picked airline is saved as its name in the current language, so `ticket.airline` stays free text. A ticket may carry a return leg (`returnFlightNo`, `returnDeparture`, and `returnAirline` only when it differs from `airline`); it is the same ticket, so the booking reference and fare are shared, and the transfer link's ticket row ends with those two columns. Its logos are files in `public/airlines/<CODE>.png`, downloaded once by `scripts/fetch-airline-logos.mjs` (run it after adding an airline) and served with the site; never load them from the logo source at runtime.
- **Stay rules are derived, never stored.** `src/lib/stayRules.ts` computes gaps, the Schengen 90/180 count and Taiwan's 183 days from the stays on every render. The Schengen list is ISO codes, so it only sees countries picked from the list.
- **The backup reminder is not plan data.** `src/lib/backup.ts` keeps its own record per year (`dnp-backup` for 2027, `dnp-backup-<year>` otherwise) (fingerprint of the last export or import). Call `markBackedUp` from any new path that writes the plan to a file the user keeps; a successful cloud push counts too, which is why signed-in users don't see the strip. `fnv1a` / `planHash` there are also what the cloud sync compares plans by, so they must only depend on what `serialize` writes.
- **Season data is fixed and hand-written** in `src/lib/seasons.ts`, keyed by stored `country/city`. Keep it consistent: twelve ratings and twelve highs and lows per city (highs above lows), every month rated 0 covered by an `avoid` note and every month rated 2 by a `best` note. No weather API.
- **Analytics never carries plan data.** `src/lib/analytics.ts` loads GA4 in the production build only (`import.meta.env.PROD`); under `npm run dev`, `track()` logs `[analytics]` to the console instead. Every event goes through `track()`, whose names and parameters are fixed in its `Events` type: interface choices, `bucket()`ed counts and flags only, never places, dates, flights, notes or typed text. Fire events from callbacks (`App.tsx`, dialogs), not from views' drag logic. [ANALYTICS.md](ANALYTICS.md) holds the event plan and a checklist: **tick or add its items in the same piece of work whenever tracking code or the GA setup changes**, and keep the README privacy table in step with what is sent.
- **Profile settings are per browser, outside the plan.** `lib/profile.ts` keeps `dnp-profile` (avatar, nickname, home, passport, tax residence, temperature unit, backup interval), edited on the settings page (`profile/index.html`, `src/profile/`). Read it with `getProfile()` where it is used, never into a module-level constant; the planner picks up changes on its next load. It changes results in place: `checkSchengen` reports nothing for EU / EEA / Swiss passports, `residenceDays` counts the tax-residence country (Taiwan by default), `flightStats` adds legs from and back to home, `tempRange` converts to °F, `shouldRemind` uses the interval. It is not exported or transferred, but it is synced to `nomad.settings` when signed in (`sanitizeProfile` reads it back), and the planner remounts the toolbar (`cloudRev`) when a pull changes it.
- **Problem reports** (`components/ReportDialog.tsx`, `lib/report.ts`) are e-mailed through FormSubmit's ajax endpoint; the recipient address is in `report.ts`. They carry only what the person typed, their screenshots (shrunk to fit FormSubmit's 10MB per message) and a line of page/language/year/window/browser, never plan data. Don't send real test reports: stub `fetch` in the preview.
- **Holidays come from two places.** `lib/holidays.ts` holds the hand-written Taiwan and Australia sets for 2026 and 2027 (`holidaySets`); `lib/worldHolidays.ts` gives every other country in the plan from the date-holidays package, which is large and must stay a dynamic `import()` (App calls `loadWorldHolidays` only when `plannedHolidayCountries` finds one; never import it statically). `availableHolidaySets` joins them for the menu, and toggles are keyed by country code in `dnp-holidays`, absent meaning off. A hand-written set wins for its country in the years it covers.
- **Visa rules are a bundled snapshot, read by passport.** `lib/visa.ts` reads `src/data/visa.json` (rebuilt by `scripts/build-visa-data.mjs` from passport-index-data, with the dataset's date as its argument) through a dynamic `import()`, which App starts only when the profile has a passport; keep it lazy. `visaFor(country)` is null without a passport, before the data loads, for the passport's own country and for places the data doesn't list, so every visa line and warning simply disappears then. `OVERRIDES` there holds documents the dataset can't express (Taiwan → China permit). Long-stay programs (`lib/longStay.ts`) are hand-written like the cities page: every text in zh, en and ja, an official `url` and non-empty `sources`, dated by `LONG_STAY_UPDATED`; `passports` restricts a program to listed nationalities, and `longStaysFor` shows nothing without a passport or where it moves freely. `visaOverstays` treats back-to-back stays in one country (ghosts included) as one visit and skips Schengen, which `checkSchengen` owns.
- **Coordinates** come from Nominatim via `src/lib/geocode.ts` (rate-limited, cached) and are shared through the `useCoords` hook.
- **The cities page is static content.** `cities/index.html` + `src/cities/` shows the ten cities in `src/lib/nomadCities.ts`: hand-written records, never scraped, with `country` / `city` stored exactly as a stay stores its place (ISO code, listed English name) so an entry can become a stay and `seasons.ts` finds its months by the same key. Every text field (`visa`, `pros`, `cons`, `article`) has zh, en and ja written out, no fallback; `sources` lists where the numbers came from and is never empty; the one-line taglines live in the dictionaries as `cities.tagline.<id>`. The page reads no plan, no profile and no network; it only fires the page view, since a city id is a place and places never go into analytics. Figures are rough and dated (October 2026); say so in the page copy rather than promising freshness.

- **The iOS app is a second client, read-only** (`ios/`, SwiftUI, iOS 17+; see `ios/README.md`). It signs in with Google through supabase-swift against the same project, schema `nomad` and anon key as `lib/cloud.ts`, and only ever selects `plans` and `settings`: it never writes a row, so `lib/sync.ts` stays the single owner of the sync rules. `ios/NotWFHCore` is a Swift package porting the pure parts of `src/lib`: `Plan.swift` mirrors `serialize` / `sanitize` field for field (a new `Stay` or `Ticket` field goes there too), `Days.swift` counts days since 1970-01-01 in UTC instead of per-year timelines, `StayRules.swift` carries the Schengen and free-movement lists (keep them equal to `stayRules.ts` and `profile.ts`), `Itinerary.swift` is `MobileItinerary`'s now / next logic. Its tests are XCTest and need Xcode; without Xcode, `swift build` in the package still type-checks it. The Xcode project is generated from `ios/project.yml` with XcodeGen and is not committed; strings live in `Localizable.xcstrings` in all three languages, like the dictionaries. The sign-in redirect `notwfh://auth-callback` is a dashboard setting (Additional Redirect URLs), like the web app's. Nothing in `ios/` is a build input of the site, so the docs hook doesn't watch it; keep this section, `ios/README.md` and the README structure lists in step by hand.

## Conventions

- No UI framework, state library or drag-and-drop library. Interactions use native pointer events.
- Styles are plain CSS using the custom properties on `:root`. A component's rules go in the `.css` file beside it, imported by that component; only tokens and things several components share go in `src/styles/base.css`. `main.tsx` imports base before `App` so component rules win ties.
- The dialog shell class is `.editor` (in `components/Dialog.css`), shared by every dialog inside a `.backdrop` (which blurs the page). A dialog is three children: the `h2` title and the `.buttons` footer stay put, and everything between goes in `.dialog-body`, the only part that scrolls. A dialog without buttons just ends with the body.
- Every page header is a `components/PillNav` (`<PillNav className="x-nav">`): it sticks to the top and folds into a frosted pill on scroll. `PillNav.css` owns the sticking, the pill and the transitions; the page's stylesheet sets only the bar's resting padding, gap and contents (and, for the planner, what shrinks under `.topbar.pill`). The bar is absolutely positioned inside a slot whose height is measured, so never give the bar a margin (put it on `.x-nav-slot`) and never make its resting height depend on scroll state.
- Typefaces are IBM Plex Sans for Latin (Google Fonts, 400 and 600 loaded) and Glow Sans TC (未來熒黑, via emfont, 400 and 500 loaded) for everything else, in that order in the stack so Latin glyphs come from Plex. CSS uses two weights only: 400 and 600; Glow Sans has no 600, so a 600 element gets Glow's 500 beside Plex's 600, which were chosen to match. Do not introduce 500 or 700, and load no other weights. The pages' `<link>`s and `FONT` in `lib/exportPng.ts` name both families. The one exception is the tagline under the title (`.tagline`), set in a pixel face per language, all 400: Pixelify Sans (en) and DotGothic16 (ja) from Google Fonts, the latter requested with `text=` for just the tagline's characters in both `index.html` and `app/index.html`; and 俐方體 11 號 / Cubic 11 (zh) from `src/assets/cubic11-tagline.woff2`, a 19-glyph subset made by `scripts/subset-tagline-font.mjs` from the full font (not in the repo). Changing a zh tagline means re-running that script; changing a ja one means updating the `text=` in both pages. Do not use these faces anywhere else.
- The product name is per locale: `app.title` is 今天不在家工作 (zh), Not WFH (en) and 今日は在宅じゃない (ja) — the same "not working from home" joke in each language's remote-work slang; `app.tagline` (A Digital Nomad Planner) is English in every locale and is used for the document title and the PNG export. Static HTML titles and link-preview tags spell out all three names, since crawlers never see the interface language. The line under the page title is `components/Tagline.tsx`, which types `app.tagline.1`–`.3` (per language) in turn once per page load and stops on the last; a language switch afterwards shows the new last line without replaying. The year is not part of the name; neither the page header nor the PNG export shows it.
- The header mascot (`components/PixelNomad.tsx`) is pixel art written as rows of characters, one per pixel, rendered to SVG rects and animated by swapping two frames in CSS. Edit the frame strings, not SVG paths; keep it decorative (`aria-hidden`). It is the brand mark and stays separate from the avatar.
- The paper-doll avatar (`lib/avatar.ts`, drawn by `components/Avatar.tsx`, picked with `profile/AvatarPicker.tsx`) uses the same character-per-pixel idea in layers on a 32×32 canvas with a 16×24 front-facing figure in the middle. An 8-character row is the left half and is mirrored, 16 is the full figure width, 32 the full canvas; letters are colour codes resolved per avatar, so draw a shape once. Rows count from the figure's top (negative rows reach above it); things beside the figure are 8 columns, drawn for the left and mirrored, standing on the floor. `X` / `x` are the part's own colour. A cloth colour (`Colour`) is an index into `CLOTH` or a custom hex string; always resolve it with `clothHex`, never index `CLOTH` directly. Extras sit in independent slots (head, eyes, lower face, neck, back, each hand, each side), with `COLOURED` listing which options take a colour; `withHand` keeps a two-handed thing in both hands. `compose(avatar, pose)`: `blink` closes the eyes, `dip` sinks everything above the shoes a pixel for the idle bob, `wag` puts the animals beside the figure in their second frame, `only` draws just the figure or just what stands beside it, `focus` paints one slot in colour and everything else in one grey, or with `bare` leaves everything else out (the picker's tiles: face slots keep the silhouette, the rest are drawn alone and `<Avatar bare>` zooms to them), `view: 'back'` draws the figure from behind from the `*_BACK` tables (a slot with no back shape, such as the eyes or the hands, is left out; sides swap). A new option that shows from behind needs its back shape too, or it vanishes when the figure turns. `<Avatar animate>` layers these so the figure and the animals loop on separate beats; with no pose, `compose` gives the still image the PNG uses. A new option needs its id in the slot's list, its shape, a name under `avatar.<slot>.<id>` in all three dictionaries (hands use `avatar.hand`, sides `avatar.side`), and, if it takes a colour, its entry in `COLOURED` and a starting colour in `DEFAULT_COLOUR`; nothing else (`sanitizeAvatar` reads the lists). Pickers change a slot through `withOption`, which applies that default. Presets are named `avatar.preset.<id>`. Unlike the other profile settings, the character is saved with its own button (the page warns before leaving with it unsaved), and `profile.avatar` is null until it is: the toolbar's settings link shows it as a bust (`FACE_CROP`) and both PNG layouts draw it only when it is set.
- Icons are Phosphor at `weight="bold"`, imported per icon from `@phosphor-icons/react/dist/csr/<Name>`. Flags use `flag-icons` via `src/components/Flag.tsx`.
- **Every UI string goes through `src/lib/i18n.tsx`.** Add the key to the `zh`, `en` and `ja` dictionaries and use `t(key, vars)` (or `tr()` when a placeholder is a React node). Never hard-code display text in a component. A component that shows text calls `useLocale()` once so it re-renders on a language switch. Date and length text comes from the helpers in `lib/weeks.ts` and `daysText()`, which already follow the locale.
- Chinese strings are Traditional Chinese (Taiwan usage). Code, comments and commit messages are English.
- `HelpDialog` holds its prose per language rather than in the dictionary; change all three versions together.
- Locales are listed in `LOCALES` in `src/lib/i18n.tsx`; the language button calls `nextLocale()` to cycle through them, and `lang` attributes come from `langTag()`. Cities (`lib/cities.ts`), airlines (`lib/airlines.ts`), season notes (`lib/seasons.ts`) and changelog entries have no Japanese text and show English for `ja`; holidays (`lib/holidays.ts`) and country names (`lib/flags.ts`, via `Intl.DisplayNames('ja')`) do have it. Any new per-locale data must handle `ja`, by translation or by an explicit English fallback.
- Anything new that talks to the network must be listed under "資料與隱私" in the README.
- `src/components/HelpDialog.tsx` is the in-app guide. When a control, shortcut, or how data is stored or exported changes, update its text too.
- Dialogs call `useScrollLock()` so the page behind them doesn't scroll. On a phone the dialog shell and the ⋯ / year menus become bottom sheets (CSS only, under `NARROW_QUERY`); a menu renders a `.menu-scrim` sibling so a tap outside closes it without reaching the page.
- Hover styles that change a background go inside `@media (hover: hover)`, so they don't stick after a tap on touch screens.
- A bordered control's hover is the same 2px dark ring as its open / on / focused state: `outline: 2px solid var(--text); outline-offset: -1px; border-color: transparent`. The ring is there at rest in transparent (`outline: 2px solid transparent; outline-offset: -1px`) and hover only changes `outline-color`, so it fades in with `transition: outline-color`; a control that overrides `transition` should keep `outline-color` in its list. Buttons get it from `base.css` through `--hover-ring` (the outline style); a button with no border of its own (`border: 0`, close buttons, menu items, tabs) sets `--hover-ring: none` beside its `border: 0`, or it grows a ring on hover.
- When a property needs a `-webkit-` copy (`backdrop-filter`), write the prefixed line first and the standard one last: the production build's CSS minifier merges the pair and keeps only the last, and Chrome ignores the prefixed one. The dev server doesn't minify, so this only shows up after `npm run build`; check `dist/assets/*.css`.
- **Motion has tokens and two helpers.** Easing and durations are `--ease-out`, `--dur-fast`, `--dur-base` and `--dur-exit` on `:root` in `base.css`; animate transform and opacity only, and never during a drag (`.track.dragging` turns transitions off). Anything rendered conditionally that should leave with an animation goes through `hooks/usePresence.ts` (a menu or popover: render while `shown`, add `.leaving`) or `components/Presence.tsx` (a dialog, card or strip in `App.tsx`); the exit length is read from `--dur-exit`, which the reduced-motion media query sets to zero, so never wait for an animation event. A menu, popover, card or chip enters with `pop-in` and leaves with `pop-out` (both in `base.css`), and its own stylesheet sets `transform-origin` to the corner of whatever it hangs from; on phones the sheets keep `sheet-up` / `sheet-down`. Plan changes that aren't a drag's own pointer moves go through `changeStays` / `undoPlan` in `App.tsx`, which wrap `setStays` in `withTransition` (`lib/motion.ts`, the View Transitions API); the timeline blocks, month bars and list rows carry a `view-transition-name` from `transitionName()`, unique per element. A stay that changed gets a ring from `components/Flash.tsx`; numbers that change roll with `hooks/useTween.ts`. New tokens, keyframes or rules go into the Motion section of `DesignSystem.tsx`.
- Dates are picked with `components/DatePicker.tsx` (ISO strings in and out), not `<input type="date">`.
- **The design system page** (`design/index.html`, `src/design/`) is dev-only: it is not a build input, so it is served by `npm run dev` and never published. It imports the real `base.css` and component stylesheets, so restyling a component shows there with no change; a new token, base component or state goes into `DesignSystem.tsx` by hand, and so do changes to the hard-coded sizes it lists. `forceStates.ts` copies every `:hover` / `:focus` / `:active` rule onto `.is-hover` / `.is-focus` / `.is-active` so states show at rest. Its text is Chinese only and skips the i18n dictionaries, as does the pixel guide below.
- **The pixel style guide** (`pixel/index.html`, `src/pixel/`) is the other dev-only page: the rules behind the avatar and the mascot (grid, palette, layers, crops, motion, scaling, brand use), with every picture drawn live by `lib/avatar.ts`, so a change to a part or colour shows there at once. `src/pixel/scenes.ts` holds the 21:9 city scenes (224×96: Sydney, Tokyo, Taipei) drawn with small primitives at the avatar's pixel size; each returns two frames for its idle loop. New rules, canvases or scenes go into `PixelGuide.tsx` / `scenes.ts` by hand.
- **The demo page** (`demo/index.html`, `src/demo/`) is the third dev-only page: a row of canvases in one of the shapes in `RATIOS` (9:16 at 540×960 and 4:5 at 540×675, half a 1080×1920 reel or a 1080×1350 post, picked with a switch in the header) each holding one real app component at its own size, centred, for recording reels. A canvas is an entry in `REELS` in `Demo.tsx` (id, title, note, render); the component inside is the real one, wrapped in `.editor.demo-card`, a card the stay editor's width with its field styles (`.wide` for the avatar picker, `.demo-row` for a bare row). A component that would write to `localStorage` on its own must be controlled there: `YearSelect` takes optional `value` / `onChange` for this and otherwise calls `setYear`. It reads no plan and fires no analytics; its text is Chinese only. `scripts/record-picker-demo.mjs` records its country + city canvas to video: it builds the demo page in production mode into a temp folder, drives it in headless Chrome (playwright-core, the installed Chrome) with real input and a drawn cursor, records in slow motion (`SLOW`, default 3) with the page's timers, frame clock and CSS animations slowed to match, squeezes the logged main-thread stalls out, and encodes with ffmpeg. Its scenes select by the picker's class names (`.combo-list`, `.combo-more`, `.combo-less`, `.combo-clear`, `li.typed`), so renaming those means updating the script; re-record after changing the picker.

## Verifying changes

- Use the preview (`.claude/launch.json`, name `dev`) and check behaviour in the browser, not just types.
- The preview shares one `localStorage` with whoever is using that browser. Before seeding test data, check `dnp-plan-<year>` (and `dnp-year`) are as you found them, and remove what you added afterwards. Never clear existing plan data.
- Pointer interactions can be exercised with synthetic `PointerEvent`s; stub `Element.prototype.setPointerCapture` first, since capture fails for synthetic pointer ids.
- Say plainly what was verified by simulation and what was not tried with a real mouse, trackpad or touch screen.

## Deployment

The site has five entries: `index.html` is the landing page (`src/landing/`) at the root, `app/index.html` is the planner at `/app/`, `changelog/index.html` is the changelog page (`src/changelog/`) at `/changelog/`, rendered from `CHANGELOG.md` by `lib/changelog.ts` at build time, `profile/index.html` is the settings page (`src/profile/`) at `/profile/`, and `cities/index.html` is the cities page (`src/cities/`) at `/cities/`. The landing demos are the real components on a sample plan (`src/landing/sandbox.tsx`): it never goes through `setStays`, writes no `localStorage` and looks up no coordinates; a component that would otherwise reach the visitor's data or settings takes an opt-out there (`MobileItinerary isolated`, `ShareDialog silent`, a controlled `YearSelect`, a zoom that isn't saved), so keep that true when adding a demo. Link-preview tags in both (`og:url`, `og:image`) hold absolute GitHub Pages addresses; change them if the site moves. `public/og.png` is a hand-made static image, not generated by the build: redo it when the name, mascot or look changes. The meta description is one trilingual string (Chinese, English, Japanese) because crawlers read the static HTML and never see the interface language; keep all three in step.

Pushing to `main` publishes the site to GitHub Pages through `.github/workflows/deploy.yml` (https://simonlin7972.github.io/digital-nomad-planner/). A push is therefore a release: make sure `npm run build` passes first. The build uses `base: './'`, so keep asset references relative.
